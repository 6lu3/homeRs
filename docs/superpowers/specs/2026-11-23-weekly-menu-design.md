# 日常工具页 + 每周菜单 设计

日期：2026-11-23　状态：待确认

## 意图与原因

家里的物资清点应用目前管"有什么"，不管"打算吃什么"。用户希望有了每周菜单之后，能清楚知道这周要买什么菜。
所以做两件事：
1. 新增「日常工具」页，作为以后放各种小工具的入口页；
2. 第一个工具是「每周菜单」：按周一到周日、每天早/午/晚三餐编辑，可翻看以前的周，并能据此生成采购清单。

使用者：全家人（共用同一个家庭密码），主要在手机上用。

## 目标

- 工具页：每个工具一个入口卡片，目前只有「每周菜单」。
- 每周菜单页：显示本周日期（周一～周日，含月/日），可前后翻周、一键回到本周，过去的周也可编辑。
- 每餐可以有多道菜；每道菜可以带若干食材（名称，数量选填）。
- 输入以前吃过的菜名时，自动带出上次写的食材。
- 「按本周菜单生成采购」：算出缺什么，先弹确认卡，确认后写入购物清单。
- 菜单超过 3 个月自动删除。

## 非目标 / 反目标

- 不自动扣库存。煮完饭不改库存数量（否则库存会越来越不准）。
- 不在确认采购时直接增加库存；库存只在真的买到之后才变。
- 不做食谱、营养、热量、做法。
- 不把菜单接进「变动记录」和回收站（这两个是为物品设计的）。
- 不新增底部标签（已有 6 个，手机上会挤）。

## 约束

- 零第三方依赖；Node ≥ 22.5 内置 SQLite（`node:sqlite`）；前端是单页，用 `data-view` 切换视图，没有路由。
- 沿用现有风格：「温润家居极简」，标题栏沿用物品页/图纸页最近统一的样式。
- 数据库升级方式沿用现有做法：启动时 `CREATE TABLE IF NOT EXISTS`，不破坏旧库。
- 所有接口走现有登录检查。

## 已考虑的做法

数据存储：
1. 完全拆表（菜、食材各一张表）——灵活、可独立查询和清理，代码多一些。**用户选了这个。**
2. 一周一行 JSON——最简单，但两人同时改会整周覆盖。
3. 一餐一行 + JSON——折中。

页面入口：不加底部标签，改在首页放「工具」卡片；这是我的决定。

## 已定的设计

### 入口
- 首页新增一张「工具」卡片，点击进入工具页视图（`data-view="tools"`）。
- 工具页里有「每周菜单」入口卡片，点击进入菜单页视图（`data-view="menu"`）。菜单页有返回按钮回到工具页。
- 这两个新视图不出现在底部标签栏里；进入它们时，底部标签栏保持显示，且不高亮任何标签（实现细节由构建者决定）。

### 数据表
- `menu_meals`：`id`、`date`（`YYYY-MM-DD`）、`meal`（`breakfast`/`lunch`/`dinner`），`(date, meal)` 唯一。
- `menu_dishes`：`id`、`meal_id`（外键，级联删除）、`name`、`sort`。
- `menu_ingredients`：`id`、`dish_id`（外键，级联删除）、`name`、`item_id`（可空，指向 `items`，物品删除时置空）、`quantity`（可空）、`unit`（默认空）。
- 周以周一为起点，由日期推算，不单独存周表。

### 数量规则
- 一道菜每出现一次，算 1 份。同一周里同名菜出现 2 次，其食材就按 2 份算。
- 食材的数量默认就是"按份"，不要求填具体个数。
- 若某个食材明确写了数量和单位，且单位与库存里对应物品的单位一致，才做精确比对（写的数量 × 份数 与库存比）。

### 输入联想
- 食材名输入时，联想库存里已有的物品名；选中后记下 `item_id`，用于比对。
- 菜名输入时，联想最近 3 个月菜单里出现过的菜名；选中后带出该菜最近一次写的食材（复制，不共享）。不另建"常用菜"表。

### 生成采购
入口：菜单页底部「按本周菜单生成采购」，只针对当前显示的这一周。
对本周所有食材，按名称（有 `item_id` 的优先按物品）合并后判断：
- 写了数量且单位一致：库存不够则差额进"需要买"。
- 没写数量：库存里有该物品且数量大于 0，放进"库存里有，默认够用"（默认不勾选，让用户核对）；库存里没有或已用完，放进"需要买"，数量写作"N 份"。
- 弹出确认卡，用户可取消勾选或修改，确认后写入购物清单；取消则什么都不写。
- 写入购物清单的方式：沿用现有手动条目（`shopping_extra`），备注里注明来源菜名和份数。该表没有数量列，数量写在备注里。
- 重复生成时，名称相同且未勾选的现有手动条目不重复添加。

### 自动清理
- 超过 3 个月的菜单自动删除：按 `menu_meals.date` 判断，早于"今天往前推 3 个月"的整周删除（连带菜和食材）。
- 沿用现有回收站清理的做法：服务启动时执行一次，之后定时执行。
- 副作用：菜名联想只能看到最近 3 个月。

### 菜单页外观
手机上：顶部"‹ 日期范围 ›"加"回到本周"；下面是周一到周日 7 张卡片，每张三行（早/午/晚）显示菜名；点某一餐弹出编辑窗，里面增删菜、写食材。底部是"生成采购"按钮。宽屏沿用现有的响应式处理。

## 交给构建者决定

- 接口的路径与形状、前后端文件的拆分。
- 编辑窗的具体交互（拖动排序、键盘处理等）。
- 空周、第一次进入时的提示文案。
- 食材名和物品名的匹配细节（例如是否忽略空格、大小写）。
- 样式细节，只要和现有风格一致。
- 测试：沿用 `test/` 里现有的方式。

## 我替用户做的决定（请核对）

1. 入口放首页卡片，不动底部标签。
2. 确认采购后，条目进 `shopping_extra`；在清单里点"已买"只是勾掉，**不会**自动增加库存（现有手动条目就是这样）。买回来后需在物品页添加或加数量。
3. 过去的周允许编辑。
4. 菜名联想的数据来源是最近 3 个月的菜单。
5. 单位对不上时，只看库存里"有没有"，不做数值比较。

### 审阅后补充的决定（均为我的决定）

6. 单位：`items.unit` 是自由文本，"单位一致"就是去掉首尾空格后文字完全相同（"个"和"只"算不同），不做换算。对不上就走第 5 条。
7. 手写的食材名（没从联想里选）：生成采购时用名称去库存里查找，忽略首尾空格和大小写，且只在恰好匹配到一个物品时才算库存里有；匹配到多个或没有，都当作库存里没有。
8. 同名食材既有写数量的、也有没写数量的：分成两行显示在确认卡上。写了数量的（同单位）合计后与库存比；没写数量的按份数合计。
9. 写入购物清单的备注格式：`来自本周菜单：番茄炒蛋×2 · 共 2 份`。清单里已有同名且未勾选的条目时不重复添加，也不改它的备注；确认卡上标注"清单里已有"，不勾选。
10. 保存某一餐时，用该餐编辑窗里的完整菜单替换这一餐原有的菜和食材。两个人同时改同一餐，后保存的覆盖先保存的；不同餐之间互不影响。
11. 3 个月清理：只删除整周都早于截止日期的周，跨截止日的那一周整周保留，避免一周被删一半。
12. 时间：前端用手机本地日期计算"本周"和日期范围；服务端清理的截止日期留一天余量，部署在哪个时区都不会误删当前在看的内容。
